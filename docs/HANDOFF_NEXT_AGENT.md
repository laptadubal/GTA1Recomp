## 0. TL;DR

Найдена и исправлена **фундаментальная ошибка: вся карта читалась
транспонированной** (зеркально отражённой относительно диагонали). CMP-сетка
`base` хранится column-major — `base[y * 256 + x]`, — а движок читал
`base[x * 256 + y]`. Город при этом оставался «похож на город», поэтому баг жил
очень долго: улицы, дома и вода были на месте, но весь рисунок был зеркальным,
а все авторские привязки (телефоны, объекты, маршруты) оказывались разбросаны
относительно геометрии. Это и есть главная причина «не похоже на оригинальную
GTA 1».

Коммит: **`7b43564`** — `world: read the CMP base grid the right way round (city was transposed)`.

Изменены:

| файл | что |
|---|---|
| `src/data/formats.h` | `blockCount()` / `blockAt()` читают `base[y * kSize + x]` |
| `src/game/world.cpp` | таблица `faces[]` транспонирована вместе с сеткой + плоские декали |
| `tests/test_formats.cpp` | координаты known-cell в новом фрейме, `kDirectionFields` = {4,5,2,3} |

`cmake --build build -j8` — чисто; `ctest --test-dir build` — **1/1 passed**.

Новые артефакты: `tools/audit_map_orientation.py` (воспроизводит доказательства),
`docs/audit/*.jpg` (before/after + топ-даун + эталон).

**Продолжение работы:** мини-карта классифицирует поверхности по CMP type
(вода/дорога/тротуар/поле/здание), а не только по цвету тайла; RGB-классификатор
остался резервом для неразмеченных данных. При прижатии viewport к границам
города фон и все динамические метки, включая стрелку игрока, используют один

В GRY также реализованы синхронные tile-анимации: полные записи `anim` теперь
разбираются, а текущие AUX-кадры загружаются в общий atlas, сохраняя remap и

## 2. Что именно поменялось в `world.cpp`

Поля блока описывают грани куба, и после исправления сетки они читаются
«как написано»:

* `left` / `right` — грани, перпендикулярные **X** (`x = 0` / `x = 1`);
* `top` / `bottom` — грани, перпендикулярные **Z** (`z = 0` / `z = 1`).

Это ровно та таблица, что в OpenGTA `drawBlock` (`top` → грань `z = 0`,
`bottom` → `z = 1`, `left` → `x = 0`, `right` → `x = 1`); texSet: top=1,
bottom=0, left=2, right=3. Прошлая таблица была транспонирована
(`left/right` → края по Z, `top/bottom` → края по X) — именно это описано в
§5 старого хендоффа как «расхождение 90°, требующее разрешения». Вопрос
**закрыт**: прав OpenGTA, расхождение было следствием транспозиции сетки.

Плоские декали (заборы/перила) в старой ветке были перепутаны местами; теперь:

* пара `top`/`bottom` → вертикальная плоскость на ребре `z = 0`;
* пара `left`/`right` → плоскость на ребре `x = 0`.

(OpenGTA рисует ровно одну двустороннюю плоскость на этих же рёбрах.)

## 3. CMP route-данные: полицейские маршруты и маршруты roadblock

В CMP после блоков и объектов лежит **route network** — `routeSize` байт
(`NYC 2423`, `SANB 3576`, `MIAMI 4416`). Формат (проверен побайтово,
парсится до конца во всех трёх городах):

```
repeat:
  u8 num_vertices
  u8 route_type
  num_vertices * (u8 x, u8 y, u8 z)   // мировые координаты клетки, z = высота
```

* `route_type == 255` — **полицейские маршруты** (NYC 22, SANB 36, MIAMI 40);
* `route_type == 0..253` — нумерованные **маршруты roadblock**, на которые
  ссылаются объекты traffic-light boxes;
* `route_type == 254` — только NYC, одна запись; форматная спецификация
  описывает roadblock ID до 253, поэтому тип 254 пока **не классифицирован**;
* записи содержат 1..50 вершин `(x,y,z)`; `(0,0,0)` используется как
  терминатор в этих городских файлах, а дубли вершин встречаются в данных;
* **координаты в исправленном фрейме**: `(x, y, z)` → клетка `(x, y)`, без
  перестановки. Это поддерживает вывод об ориентации, но route-данные сами по
  себе не доказывают поведение обычного городского трафика.

Это уточнение сделано по [спецификации DMA CityScape Data Structure, §2.6 и
§2.6.1](https://misc.daniel-marschall.de/spiele/gta1/cds.pdf): `255` — police,
`0..253` — roadblock. Поэтому прежнее описание `255` как пешеходных петель,
`0..28` как автомобильных маршрутов и `254` как поезда было ошибочным.
`tools/audit_map_orientation.py` и этот handoff скорректированы.

Обычный трафик пока — клеточный AI: `Game::spawnTraffic()` /
`updateTraffic()` в `src/core/game.cpp`. Он едет по клеткам, помеченным дорогой,
и теперь учитывает direction-биты CMP (выходы, разрешённые для AI-машин), но
полосы и оригинальные правила выбора поворотов/дистанции пока не воспроизведены.
Тип `255` относится к полиции, а не к пешеходам.

Wanted-полиция теперь спавнится на близких waypoint’ах CMP type-255 и следует
по кратчайшей дуге их замкнутого маршрута, пока не приблизится к игроку; затем
переходит к погоне. `tools/audit_road_network.py ALL` проверяет покрытие этих
вершин дорогами. Высоты waypoint’а берутся из фактической дорожной поверхности
CMP; поле route Z не используется как мировая Y без отдельного подтверждения.

Открытые направления работы:

1. Разобраться с roadblock-логикой `0..253`: DMA подтверждает список
   перекрёстков, связанный с traffic-light box через `rotation`; подробное
   поведение roadblock в CMP-спецификации не задано. Не выдумывать механику и
   не трактовать `rotation` как угол.
2. Сверить left/right-hand движение, смещение по полосе и поведение на
   перекрёстках по оригиналу. Текущие гипотезы о стороне полосы не доказаны.

## 4. Важные ИСПРАВЛЕНИЯ к `docs/WORLD_AUDIT_HANDOFF.md`

1. **Соответствие STYLE ↔ город взято из данных, а не из головы.**
   Байт `CMP[4]` = `style`: **NYC = 1 → STYLE001**, **SANB = 2 → STYLE002**,
   **MIAMI = 3 → STYLE003**. (Совпадает с grandtheftwiki: style001 Liberty,
   style002 San Andreas, style003 Vice City.)
   ⚠ Старый хендофф (§3, §4) разбирал тайлы **STYLE002 как «MIAMI»** — это
   **неверно**, STYLE002 — это San Andreas. Вся таблица идентичности тайлов
   (§3: 12/69/101/150/172/115/127/129/71/67) описывает **не тот город**.
2. **Cyan-wireframe трессы в MIAMI — НЕ баг.** Пункт §0b.1 закрыт.
   Это авторский тайл **STYLE003 SIDE 71** — голубая X-ферма (проверено
   рендером тайла). В STYLE002 (San Andreas) тайл 71 другого цвета — отсюда и
   родилась легенда про «съехавшую remap-палитру». Палитра ни при чём,
   `remap` тоже.
3. Расхождение 90° (§5) — закрыто, см. §2.
4. Типы CMP-маршрутов уточнены по спецификации DMA: `255` — полиция,
   `0..253` — roadblock, `254` по этой спецификации не объяснён. Старое
   утверждение, что эти данные задают обычный трафик/пешеходов/поезд, неверно.
   Direction-биты в `typeMap[0..3]` — отдельные флаги допустимых направлений
   AI-машин; текущий трафик учитывает их через `World::roadDirectionMask`.
   `World::trafficSurface` выбирает поверхность по авторитетному
   `blockType()==2`: обычно метка стоит над видимым lid, но часть дорог
   размечена на самом lid-блоке. Серый RGB-классификатор ошибочно включал
   тротуары и пропускал часть настоящих дорог. `isPassable()` остаётся
   отдельной, более широкой проверкой для перемещения игрока пешком/на авто.
   `tools/audit_road_network.py ALL` считает type-2 клетки и допустимые выходы
   во всех городах; оставшиеся клетки без выхода надо проверять по исходным
   direction-битам/границам карты, а не «чинить» текстуру автоматически.
   Аудит также считает weak connectivity с сохранением raw Z и CMP-направлений:
   компонентов NYC/SANB/MIAMI сейчас 17/31/9, крупнейшие содержат
   19,006/18,969/19,623 road-level nodes. Малые компоненты выводятся с bbox
   для проверки островных дорог и эстакад; разные высоты автоматически не
   объединяются.
   Два SANB singletons `(28,225,rawZ2)` и `(41,226,rawZ2)` используют lid 23
   и не имеют геометрически соседнего road-level. Сам lid 23 встречается в
   161 размеченной дорожной клетке города, поэтому одиночный вид не доказывает
   повреждение графики или CMP; не создавать соседей искусственно.
5. Пункты §0b «РАЗРЕШЕНО измерением» 1–6 остаются в силе, но помните, что
   измерения делались в **транспонированном** фрейме; часть выводов о
   конкретных клетках (например «канал cells 49–59, 194–196») относится к

## 5. ОТКРЫТЫЕ ЗАДАЧИ (по приоритету)

### A. Ротация lid — правило теперь исправлено, нужна runtime-приёмка
Раньше формула в `world.cpp:emitLidUV`:

```cpp
const int k = (4 - rotation - j) & 3;
```

Эта формула отражала обход UV-углов. После сверки с OpenGTA (`gl_cityview.cpp`,
rotation добавляется к UV corner index) правило заменено на чистую циклическую
ротацию `(rotation + j) & 3`, а `tools/preview_map.py` обновлён синхронно.
Симптом до исправления: в MIAMI на `--spawn 122,128` дорога
выглядела «пятнисто» — короткие жёлтые поперечные штрихи не совпадали с
ориентацией соседних участков. Проверить все города офлайн:
`python3 tools/preview_map.py NYC|SANB|MIAMI`; затем нужна игровая приёмка на
MIAMI (122,128), NYC (108,108) и на рампах/поворотах.

Ориентир: OpenGTA, `gl_cityview.cpp` — `jj = 0; if (typeMap & 16384) jj += 2;
if (typeMap & 32768) jj += 4;` и далее `SLOPE_TEX_CP`/`GLTEX_HELPER`
(у нас `rotation()` = `jj / 2`).

### B. Звук — первый этап интеграции сделан, нужна игровая приёмка
* `src/main.cpp` теперь выбирает `LEVEL001/002/003.SDT` по `map.style` (NYC /
  SANB / MIAMI) и загружает новый банк при смене города.
  (`LEVEL000` — 16 записей, спектр похож на белый шум, в игре, судя по всему,
  не используется: города 0 не существует.)
* **Двигатель синтезируется синусом** (`AudioManager::mix`, `baseFreq` и т.д.).
  Оригинальные loop-сэмплы двигателя найдены и опознаны: это записи
  **`id = 79 + car.sprNum`** (диапазон 79..125). Признаки: `edge ≈ 0.00–0.04`
  (бесшовная петля), все на 5500 Гц, узкие тональные пики (1225 Гц, 1696 Гц,
  575/848 Гц, 1252 Гц), `env` стационарная. Записи 79..99 идентичны во всех
  трёх банках, 100..125 — город-специфичные, что точно совпадает с тем, что
  `sprNum 0..20` — общие машины, `21..28` — городские. Формула `79 + sprNum`
  даёт максимум 107 — внутри диапазона.
  В `AudioManager` этот loop уже играет зацикленно с интерполяцией и питчем от
  скорости; синтез остаётся fallback, если для текущей машины сэмпл недоступен.
  `Game::updatePlaying()` передаёт `79 + sprNum` для машины игрока.
  Нужна слуховая приёмка в трёх городах и настройка диапазона pitch/громкости.
* `playSfx(id)` в `game.cpp` использует id 12/13/14/19/37/39/43/44/49/53/56/59/66.
  Их соответствие оригиналу **не подтверждено** — это предположения прошлых
  агентов. Проверяемых таблиц id в `GTA8.EXE` нет (только `GUN_TRIG`,
  `EXPLODE` в SETSOUND-скрипте). Если возьмётесь — сверяйте по спектру/длительности.

### D. Дорожные метки CMP и оставшаяся проверка
`roadSurface`, трафик, миникарта и чистый дорожный проход теперь используют
авторский `blockType == 2` в CMP (обычно выше текстурного lid, иногда на самом
lid), а не только цветовую эвристику. Если сам видимый блок помечен type 2,
эта метка имеет приоритет над другим type на блоке выше; иначе используется
ненулевая метка над поверхностью. Это сохраняет 66 дорог NYC и 12 MIAMI,
которые раньше терялись из-за верхних метаданных. Метка типа 2 также авторитетна на
эстакадах, поэтому высотный cutoff снят; `isPassable()` явно пропускает такие
дорожные деки поверх зданий. `tools/audit_road_network.py ALL` считает для
NYC/SANB/MIAMI 18,903 / 19,177 / 19,584 дорожные клетки; 442 / 151 / 91 из них
имеют lid вне grey-asphalt эвристики, но это не исключает их из дорожной сети.
Трафик кэширует все road lids в колонке, а не только верхний: это 19,186 /
19,349 / 19,767 road-level nodes в NYC/SANB/MIAMI, с 167 / 100 / 16 колонками,
где CMP содержит несколько уровней дороги. Поэтому улица под эстакадой остаётся
доступной трафику, а выбор следующего уровня сопоставляется с текущим raw Z.
Игрок-машина также сохраняет raw Z дорожного яруса, проверяет четыре угла
коллизии на этом же ярусе и переходит на соседний уровень только через
соседнюю дорогу/рампу. Это исправляет прежнее поведение, когда физика игрока
проверяла только верхнюю дорогу столбца и могла блокироваться на улице под
эстакадой либо перескакивать на верхнюю поверхность.
При той же логике surface-type, что в `buildMinimap`, цветовой fallback
добавляет поверх CMP-разметки только 1 / 6 / 0 асфальтовых клеток соответственно;
раньше диагностический скрипт ошибочно считал тип `-1` для поверхностей без
блока над ними и завышал расхождение. Текущий отчёт отдельно разрешает тип
видимого блока и traffic-road tag.
CMP police routes type 255 проверены: замкнуты 22/22, 36/36, 39/40 маршрутов;
на CMP type-2 дорожную поверхность в той же клетке попадают 629/631, 994/1022
и 1236/1242 waypoint’ов. Если той же высоты нет, runtime теперь привязывает
waypoint на соседнюю клетку только при точном совпадении raw Z: audit находит
2/12/6 таких точек NYC/SANB/MIAMI. SANB дополнительно имеет 6 точек с дорогой
в той же клетке на другом уровне и 17 без дороги даже в соседних клетках;
NYC/MIAMI имеют 0/2 оставшихся точек без дороги. `tools/audit_map_orientation.py` теперь сверяет маршруты именно с
авторским CMP-тегом типа 2, а не с серой палитровой эвристикой; телефоны из
`MISSION.INI` проверяются только для NYC.
Wanted-полиция использует ближайшие авторские loops для подхода, берёт уровень
дороги из route Z (проверенная на retail data формула `rawHeight = 5 - routeZ`)
и переключается на погоню рядом с игроком. Погоня теперь сохраняет raw road
level и проверяет соседнюю поверхность/рампу на том же ярусе; respawn полиции
заново выбирает верхний ярус дорожной клетки вместо сохранения старого уровня.
По `tools/audit_road_network.py`
формула находит уровень точно для 629/631 NYC, 987/1022 SANB и 1234/1242 MIAMI
waypoint’ов; в остальных клетках, где дорога есть, берётся верхний уровень.
Незамкнутый маршрут в MIAMI не замыкается искусственно.
Трафик не считает slope-стыки тупиками только из-за сглаживания уровня:
если CMP direction flag разрешает шаг, сырой уровень соседних дорог различается
на 1 и slope одной из клеток направлен вдоль шага, соединение принимается.
Высота машины на рампе интерполируется. Аудит возвращает 28 направленных
соединений в NYC и 42 в SANB. В графе всех road levels 19,129/19,186,
19,297/19,349 и 19,725/19,767 уровней имеют допустимый выход; остаются 57/50/42
road-level nodes, где CMP flags блокируют все геометрические соединения, и два
тупика без соседа в SANB. Ещё четыре разрешённых SANB-соседа имеют raw-разницу
2, а шесть — raw-разницу 1, но все эти клетки плоские; не соединять их без проверки.
Счётчик `surface type-2 tags with another type above` показывает 66 клеток
NYC и 12 MIAMI с конфликтующими метаданными над дорогой. Эти клетки теперь
разрешаются в пользу явного типа самой поверхности; аудит подтверждает, что
их дорожные ярусы имеют разрешённый выход. SANB таких клеток не имеет.
Остаётся проверить визуально, что именно эти редкие варианты — полосы,
перекрёстки и нестандартные покрытия — корректно выглядят при `cleanRoads`.
Текущая среда не даёт OpenGL display: запуск с `SDL_VIDEODRIVER=offscreen`
завершился `Could not initialize OpenGL / GLES library`, поэтому runtime screenshot
пока не получен.
В `classifyRoadLids` также есть неинкрементируемый `structure`; поскольку
структурный фильтр влияет только на опциональную графическую замену, починить
его после визуальной приёмки либо убрать.

### E. Известные проблемы из §0b (проверить актуальность после фикса)
Плотность/дубли объектов, slopes/UV, камера/масштаб (tilt 72/60/82, fov 34,
viewHeight 11), честный отчёт остаточных расхождений.

## 6. Команды и грабли окружения

```
cmake --build build -j8
ctest --test-dir build --output-on-failure        # 1 тест

pkill -f dos_gta_recomp; sleep 1
GTA_NOSWAP=1 ./build/dos_gta_recomp --data game_data/GTADATA --city MIAMI|NYC|SANB \
  --screen game --spawn X,Y --screenshot /tmp/x.bmp --frames 12 --fixed-dt 0.016
sips -s format png /tmp/x.bmp --out /tmp/x.png
```

* macOS: **нет `timeout`**, **нет PIL/numpy** в `python3` из PATH. Бандленный
  интерпретатор с numpy/Pillow:
  `/Users/kitbag/.dsh/dsh-runtimes/dsh-primary-runtime/dependencies/python/bin/python3`.
* `GTA_NOSWAP=1` обязателен для скриншотов: оконный сервер вешает
  `SDL_GL_SwapWindow` (дедлок `Cocoa_GL_SwapWindow`), скрин читается из
  `resolveFbo_`.
* `GTA_DBG=nosides|nolids|nofloor|idcolor|cellcolor|floorcoord`.
* Симуляция **недетерминирована** (трафик/AI) — full-frame diff между запусками
  бессмысленен.
* `/tmp` чистится: скрипты прошлой сессии (`seam_proj.py`, `profile.py`,
  `proj_road.py`, `check_footprints.py`) уже потеряны. Всё, что нужно
  следующему агенту, кладите в `tools/`.
* `.deploy/` — untracked, не коммитить.

## 7. Не проверено / риски

* **Визуальная приёмка пользователем не сделана.** Фикс меняет облик города
  целиком (это зеркальное отражение), поэтому «стало лучше» должен подтвердить
  человек. Скриншоты для сравнения — в `docs/audit/`.
* Пункт A (ротация) **не** проверен измерением; вывод о необходимости правки —
  гипотеза из формы формулы, а не доказательство. Не принимать на веру.
* Метрика покрытия сторон инвариантна (см. §1) — не использовать как аргумент.
* Проверка телефонов в C++-тесте **удалена** (я добавил её и получил 0/128
  из-за неверного ожидания `pz - 1`; правильный критерий — «этаж, не здание»,
  см. §1). Если будете возвращать тест — используйте критерий «floor vs
  raised», он даёт 128/0 против 82/45.
